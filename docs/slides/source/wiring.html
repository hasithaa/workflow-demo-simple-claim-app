How the apps plug in

Expenses · Ann

Talks to the Claims API we built

/api/claims → :9090/claims

POST /claims sends the claim, with an id the app picks. That id becomes the workflow id.

POST /claims/{id}/bill sends the bill's link to the waiting workflow.

GET /claims reads the status the workflow records at each step.

Approvals · Jane

Talks to the built-in Management API

/api/workflow → :8234/workflow

Each call says who is asking: x-user-id and x-user-roles: MANAGER.

GET /human-tasks lists only the tasks Jane may act on, with the claim and bill link.

POST /human-tasks/{id}/complete sends her decision; the workflow carries on.

Neither app knows the steps of the process. Change the workflow, and the apps keep working.

The apps are wired to two APIs. Expenses calls the Claims API we built: submit with an id it picks, which becomes the workflow id; send the bill to that id; read the status. Approvals calls the Workflow Management API that ships with the runtime, saying who is asking with two headers. It only ever sees the tasks that person may act on, and completing one hands the decision back to the workflow. Neither app knows the steps, so the process can change without touching them.
